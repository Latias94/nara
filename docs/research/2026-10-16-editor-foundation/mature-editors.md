# Mature editor architecture: transferable boundaries for Nara

Date: 2026-10-16. Status: research evidence and recommendations, not an implementation contract.

Scope: Godot source at `d824ca9fe29137edbcbf682f1bafabb74a435eab`, Unity 6.3 documentation, and Epic's current Unreal documentation. Local Godot references below use the inspected commit; Unity and Epic links are official sources. No build, platform execution, or Nara GUI migration was performed for this note.

## Findings

The transferable idea is an editor product with explicit documents, transactions, workspaces, extensions, and native resource ownership. The engines do not demonstrate one mandatory widget architecture. Godot shares its engine scene/UI foundation. Unreal exposes Slate and wraps Slate controls through UMG. Unity supports several UI systems and recommends UI Toolkit for complex editor tools. Therefore, sharing Nara's renderer is a useful direction, while adopting the runtime game UI as the editor's complete widget system remains a separate decision. [Godot Control](https://github.com/godotengine/godot/blob/d824ca9fe29137edbcbf682f1bafabb74a435eab/scene/gui/control.h#L45), [Unreal UWidget](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/UMG/Components/UWidget?application_version=5.5), [Unity UI comparison](https://docs.unity3d.com/6000.3/Documentation/Manual/UI-system-compare.html).

## Godot: share foundations, separate responsibilities

Godot's current dock API is `EditorPlugin::add_dock`/`remove_dock`. Older `add_control_to_dock` and bottom-panel APIs are deprecated compatibility paths. `EditorDock` derives from `MarginContainer`; `EditorDockManager` separately exposes open, close, focus, floating windows, and configuration persistence. This is stronger evidence for separating panel identity and lifecycle from layout than for copying the legacy dock-slot enumeration into Nara. Local sources: `editor/plugins/editor_plugin.h:149-175`, `editor/docks/editor_dock.h:40`, and `editor/docks/editor_dock_manager.h:150-166`. [Current plugin documentation](https://github.com/godotengine/godot/blob/d824ca9fe29137edbcbf682f1bafabb74a435eab/doc/classes/EditorPlugin.xml#L462).

An inspector extension has bounded hooks such as `can_handle`, `parse_begin`, and `parse_property`. It contributes controls through the inspector's extension point. Plugin registration and removal are paired; Godot explicitly documents removing an inspector plugin on deactivation to avoid leaks and unexpected behavior. A dock must also be removed and freed. Extensibility therefore includes resource lifetime and cleanup, not just a global registry of callbacks. Local sources: `editor/inspector/editor_inspector.h:367-387`, `doc/classes/EditorPlugin.xml:462-510`. [Inspector registration lifecycle](https://github.com/godotengine/godot/blob/d824ca9fe29137edbcbf682f1bafabb74a435eab/doc/classes/EditorPlugin.xml#L496).

Godot's undo manager maintains separate scene histories and a global history. It associates operations with the appropriate document and detects history mismatches. This is a useful precedent for Nara's existing command/history ownership: a floating Inspector must not acquire a second undo stack for the same document. Scene identity, dirty state, save, and undo belong to the document/session owner. Local sources: `editor/editor_undo_redo_manager.cpp:43-157`. [History ownership](https://github.com/godotengine/godot/blob/d824ca9fe29137edbcbf682f1bafabb74a435eab/doc/classes/EditorUndoRedoManager.xml#L7).

The renderer sharing is concrete: `Control` derives from `CanvasItem`; the latter creates its rendering object through RenderingServer. A Viewport creates a render-server viewport and obtains its texture. However, even this engine has distinct presentation strategies: the inspected editor source notes that its 2D editor does not use a dedicated SubViewport like its 3D editor. Its GameView references an `EmbeddedProcessBase`, remote process identity, and debugger state. A game view must not be equated with either an offscreen scene texture or a dock window. Local sources: `scene/main/canvas_item.cpp:1897`, `scene/main/viewport.cpp:5598-5599`, `editor/editor_node.cpp:563`, `editor/run/game_view_plugin.h:234`, and `editor/run/game_view_plugin.cpp:504-509`. [Game view source](https://github.com/godotengine/godot/blob/d824ca9fe29137edbcbf682f1bafabb74a435eab/editor/run/game_view_plugin.cpp#L504).

## Unity: keep a stable editor product across UI generations

Unity's `EditorWindow` is a dockable or floating editor surface with lifecycle callbacks, focus, and unsaved-change behavior. Its API exposes both `CreateGUI` for UI Toolkit and `OnGUI` for IMGUI. The product concept survives different presentation systems; neither toolkit needs to define the complete authoring data model. This supports keeping Nara's document, selection, and command contracts outside egui or Dear ImGui. [EditorWindow lifecycle](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/EditorWindow.html).

`SerializedObject` provides a generic serialized-field editing stream with integration into dirty tracking, undo, and prefab override presentation. The documentation also warns that independent streams require synchronization. The lesson for Nara is to retain one authoritative editing path and refresh presentation models after accepted commands, rather than making every Inspector own a mutable copy of the document. This is an architectural inference, not a proposal to reproduce Unity's serialization system. [SerializedObject](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/SerializedObject.html).

Unity's Undo documentation explicitly treats component addition, object creation/destruction, and reparenting as undoable operations. Generic authoring is therefore larger than editable scalar fields. For Nara, schema-driven component creation and structural commands should be completed in the toolkit-independent path before a new GUI is treated as an editor capability upgrade. [Undo operations](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Undo.html).

## Unreal: targeted extension points and explicit module lifetime

Unreal separates editor modules from runtime modules. Its editor-module guide uses startup and shutdown functions to register and clean up editor features, with explicit dependencies on runtime game types and Slate. It does not require shipping builds to carry the editor customization module. Nara can follow the dependency direction with ordinary statically linked Rust crates and functions; a dynamic plugin loader is unnecessary to establish modularity. [Editor module structure](https://dev.epicgames.com/documentation/unreal-engine/setting-up-editor-modules-for-customizing-the-editor-in-unreal-engine?lang=en-US).

Slate's tab manager has named tab spawners and persistent layouts. Transactions and object modification are separate APIs from widget creation. This supports three independently owned concepts in Nara: a panel instance, a workspace placement, and a document mutation. Closing or relocating a tab should affect presentation lifetime without silently discarding the associated document's history. [FTabManager](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Slate/FTabManager), [FScopedTransaction](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Editor/UnrealEd/FScopedTransaction), [UObject::Modify](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/CoreUObject/UObject/Modify).

Slate's architecture guidance also favors direct access to models, avoiding duplicated state and feedback loops, and generalizing irregular tools after their use cases are understood. This argues against designing a universal cross-toolkit widget language before Nara has implemented its own real editor panels. Sharing domain state and commands is a smaller, better-supported boundary. [Slate architecture](https://dev.epicgames.com/documentation/unreal-engine/understanding-the-slate-ui-architecture-in-unreal-engine?lang=en-US).

## Recommended minimum seams for Nara

The following are recommendations inferred from the evidence above, not claims that the reference engines implement Nara's authority model.

1. **Authoring documents and commands.** Keep document identity, typed source kind, component catalog, selected objects, accepted revisions, mutation validation, undo/redo, save, and recovery in the existing session/tooling owners. Offer Scene and Prefab tree/Inspector projections without pretending a Prefab is a Scene. A GUI callback emits a command against the current projection; it does not mutate a hidden project world.
2. **Editor workspace.** Give panels stable type/instance identities, titles, visibility, focus, and small presentation state. Preserve layout separately from game assets. Begin with a finite registration table for built-in panels and a single real contributed panel. Keep toolkit-native layout payloads versioned and recoverable; do not implement a second docking engine merely to normalize them.
3. **Native host and rendering bridge.** Keep event-loop, native-window, device/queue, surface, cursor/IME, focus routing, close, and teardown authority with the editor host. Toolkit backends consume these resources through the integration boundary. Expose the engine's scene output as an owned render-view/texture bridge with explicit resize and retirement, rather than leaking toolkit texture handles into the scene model.
4. **Toolkit presentation.** Put Dear ImGui widgets, IDs, frame state, draw data, and backend texture registrations in the adapter. A later custom UI should reuse documents, commands, panels' semantic state, assets, and render services. Widget code, docking implementation, focus integration, and accessibility work can still require replacement; promise this explicitly instead of claiming a free UI swap.
5. **Bounded editor contributions.** Start with compile-time Rust contributions and deterministic registration/removal at host startup/shutdown. An Inspector contribution can consume a schema/projection and emit existing commands. Do not infer permission to execute arbitrary project Rust when the ordinary editor opens a project. Loading project extensions is a separate trust and execution policy; game mods and engine-native editor plugins are separate products too.

These boundaries address concrete failures: two Inspectors overwriting one another's stale values; detached windows keeping textures after device teardown; closing a dock destroying a document's undo history; a toolkit callback bypassing unavailable-component preservation; missing extension registrations making a saved layout unusable; or opening an asset accidentally running project code. Keep checks at the owners that can enforce those facts. Avoid duplicate proof objects and parallel mutation pipelines in each layer.

## Evidence needed before selecting the replacement adapter

A useful Dear ImGui experiment must run a real Nara Inspector command through edit/undo/redo/save/reopen, display a resized engine Scene View, and move a panel into a native secondary window. Check focus, input capture, mixed DPI, IME, layout restoration, close/reopen, texture retirement, and shutdown. Record tested OS/backend combinations. Docking inside a window, native multi-viewport windows, and multiple engine camera views are separate acceptance items. Reference-engine architecture cannot prove that the chosen Rust bindings and platform/backend combination satisfy these requirements.

Defer a universal widget tree, runtime/editor UI unification, a dynamic Rust plugin ABI, distributed editor services, and a bespoke layout serializer. Admit them only when a concrete editor workflow exceeds the bounded seams above. The desired first milestone is an editor whose existing authoring behavior survives presentation replacement, whose extension lifetime is explicit, and whose native windows and render resources have one accountable owner.
