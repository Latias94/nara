# Rust 1.100 Impact On Nara

Date: 2026-11-13. Scope: bounded research against the Rust 1.100 announcement, official release
notes and API documentation, compared with the current Nara working tree. This note recommends
follow-up work; it does not change the supported compiler, dependencies or qualification status.

Rust 1.100 offers useful build-tool improvements and two potentially useful runtime primitives:
custom allocation for `Vec`/`Box`, and `DropGuard`. For Nara, the immediate priority is to qualify
the newer compiler and Cargo against existing production workflows. No inspected use establishes
an immediate need to raise the MSRV from 1.95. Cargo's new diagnostics and build layout can be
evaluated while retaining that source compatibility target.

## Five Practical Priorities

### 1. Qualify 1.100 Alongside The Existing MSRV

The official [compatibility notes][release] identify several changes worth exercising against
Nara's real consumers:

- `Infallible` becomes an alias for the fully stabilized never type `!`. Never-type fallback
  becomes `!` on every edition. Nara already uses edition 2024, where that fallback was already
  in effect; older-edition dependencies remain relevant to the change.
- Closures capture variables used in `if let` more precisely. Trait-object dyn compatibility is
  checked in more places, and the next trait solver is enabled for orphan checking.
- Generalized `Box` implementations can cause new type-inference errors. Additional layout,
  `repr` and macro checks can change diagnostics even where the intended API boundary is sound.

Nara has concrete `Ok::<_, std::convert::Infallible>(...)` uses in
[reflection](../../crates/nara_reflect/src/value.rs),
[scene validation](../../crates/nara_scene/src/validation.rs) and
[project content](../../src/project_content.rs). These explicit annotations are a reason to
exercise those paths, not evidence that they fail. The [official alias documentation][infallible]
explicitly accommodates retaining `Infallible` when supporting older Rust versions. Replacing
these annotations with `!` would require a newer MSRV without demonstrating a product benefit.

The [Clippy 1.100 changelog][clippy] adds `option_zip_none` (`suspicious`) and
`needless_nonzero_get` (`complexity`), and broadens checks such as `redundant_clone`,
`needless_bool` and `map_unwrap_or`. It also fixes false positives involving derives, macros,
`#[expect]` and integration tests. Nara's
[module-consumer CI gate](../../.github/workflows/ci.yml) runs Clippy with `-D warnings`, so a
compiler update can change that gate independently of runtime correctness. The shared
[limit types](../../crates/nara_core/src/limits.rs) genuinely wrap `NonZeroUsize`; that is not
evidence that their necessary `.get()` calls trigger `needless_nonzero_get`.

Recommended follow-up, after the current runtime integration is ready: keep the 1.95 evidence,
then qualify an explicit 1.100 toolchain with the existing affected feature/consumer coverage.
Include the Cargo build consumer, the external module Clippy gate and relevant compile-fail
fixtures. Inspect changed `.stderr` diagnostics before considering snapshot updates, so a
different compiler error does not conceal a lost boundary check. Run Cargo sequentially with
one build job and reuse `target`. Native Editor claims still require the
[native qualification procedure](../verification/native-editor-qualification.md).

This is a recommendation for later qualification. No compiler, CI or MSRV change is made here.

### 2. Exercise Cargo Builds, Play And Packaging Against The New Artifact Layout

Cargo 1.100 reorganizes **intermediate** build artifacts to apply configuration hashes
consistently. The [announcement][announcement] describes fewer configuration/cache collisions;
the [Cargo changelog][cargo-changelog] directs tools to JSON messages because the internal
layout is not stable. This is not a promise that Nara builds will be faster or that concurrent
Cargo in this checkout is now appropriate.

Nara's production build adapter is already aligned with that guidance:

- [cargo_build.rs](../../src/project_tooling/cargo_build.rs) invokes
  `cargo build --locked --message-format=json` with explicit package, binary, profile, target
  and features. It takes the executable path from the selected artifact and captures its bytes.
- [bootstrap.rs](../../src/project_tooling/bootstrap.rs) also selects the reported executable.
  [messages.rs](../../src/project_workflow/cargo_facts/messages.rs) parses `compiler-artifact`
  records and their `executable` field. These are the official
  [Cargo JSON interfaces][cargo-json], rather than a glob over hashed intermediates.
- [CargoBuildTools](../../src/project_tooling/cargo_build/tools.rs) resolves actual Cargo/rustc
  tools in the selected workspace and revalidates them. Its
  [guide](../guides/cargo-builds.md) already distinguishes compiler identity from an MSRV label.

The candidate workflow passes `reference-game/target/release/headless` and `desktop` final
binaries to packaging, with the Windows suffix where applicable. The official
[build-cache reference][build-cache] continues to document these final profile output locations;
the intermediate-layout change alone does not establish that this packaging path is broken.

The useful follow-up is a real selected-binary build/capture and Play/export regression under
1.100, including a reused build and feature/profile selection. Inspect any measurement or
third-party tool that reads intermediate files if it fails. No source-proven layout break was
found in the inspected production adapter, so there is no justification for a speculative
directory-layout compatibility layer or a new target directory.

### 3. Use Cargo Dependency Diagnostics As Evidence Before Changing The Graph

Cargo now has its own `[lints.cargo]` system, including warn-by-default
`cargo::unused_dependencies`. The [official lint reference][cargo-lints] also describes unused
workspace entries and the limits of detection: only selected packages are checked, target
selection must cover the relevant table, dev-dependencies are not checked, and dependencies
used to activate transitive features can produce false positives.

This is directly relevant to Nara's many optional module features, platform-specific dependencies
and independent consumers. Run a later diagnostic pass over meaningful supported feature and
target combinations; review a warning against those consumers before removing a dependency.
An all-targets invocation still does not prove every feature, platform or dev-dependency unused.
Potential build-time savings are a hypothesis until an unnecessary edge is actually found and
the affected build cost is measured.

The current [workspace manifest](../../Cargo.toml) deliberately selects Bevy ECS `=0.20.0`,
Winit `=0.30.13`, Dear ImGui adapters `=0.21.0`, pinned Parley/Swash/TTF parser versions, and WGPU
revision `cddb2f5d80dc0009b2ef6767635140cacf90a007`. The separate GPUI consumer pins Open-GPUI at
`f75c10b2a9bf7b4dcb2c8c2aa446203997601369`. Its Windows feature/dependency graph is a separate
compatibility surface. The read-only reference Open-GPUI manifest currently declares MSRV 1.92;
that local reference is not proof about the consumer's pinned revision or a 1.100 build.

Retain the current locks during compiler qualification. If an older dependency fails because of
the never-type or another documented change, diagnose that exact failure and consider a focused
upstream fix. The [announcement][announcement] notes that fixes have been released for affected
public crates; it does not establish that any particular locked Nara dependency needs an update.
Installing 1.100 alone is not a reason to refresh the whole dependency graph.

Cargo also stabilizes minimum publish age, for example
`registry.global-min-publish-age = "3 days"` in Cargo configuration. The
[announcement][announcement] and [resolver reference][publish-age] explain that already locked
versions remain eligible, missing registry publish times bypass the age filter, and
`cargo install` ignores it. This is an optional policy for future registry resolution, with
explicit overrides when needed; it neither re-audits the existing lockfile nor covers a Git
revision pin. No such configuration is added here.

One further tooling change matters when updating installation instructions: ordinary
`cargo install` now uses an existing lockfile in the crate tarball by default, and its
`--locked` becomes a no-op ([release notes][release]). Nara's pinned nextest install action is
not evidence of a source-install failure; no install workflow change is needed on this evidence.

### 4. Consider DropGuard Only Where It Removes Real Local Cleanup Plumbing

The newly stable [`core::mem::DropGuard`][dropguard] owns a value, dereferences to it, and runs a
closure when dropped. `DropGuard::dismiss` returns the value without running the closure. This
supports finite local cleanup and rollback on ordinary returns, `?` and unwinding. It cannot
provide cleanup after process abort, and it does not create transaction semantics on its own.

There are real small candidates: the test-only `WorkerSpawnFailureReset` in
[task runtime](../../crates/nara_tasks/src/runtime.rs) and the local publication-fault `Reset`
in [source-tool installation](../../src/project_host/runtime/editor/source_tools/release/installation.rs).
These show possible code simplification, with no measured runtime gain. They do not justify an
MSRV bump by themselves.

Adopt it opportunistically only after a separately justified MSRV decision, or for a consumer
that already requires 1.100. Keep named domain owners where `Drop` implements a meaningful
lifetime protocol. In particular, do not replace task retirement, process containment or
publication contracts with a generic closure merely because the helper exists.

### 5. Keep Custom Allocation Behind A Measured, Complete Consumer

Rust 1.100 stabilizes the core [`Allocator`][allocator] trait and allocator-aware `Vec` and `Box`
construction. The [announcement][announcement] explicitly says wider collection/pointer
coverage remains future work. The stable unsafe trait imposes allocation validity, allocator
equivalence, growth/shrink and non-unwinding obligations. It is useful infrastructure for an
arena or bounded allocator; it does not automatically make allocations fallible or all engine
memory subject to one budget.

The concrete Input owner demonstrates both an opportunity and the current limit:

- [InputTimeline::with_limits](../../crates/nara_input/src/timeline/owner.rs) already uses
  `try_reserve_exact` for a retained `VecDeque` and a scratch `Vec`, reporting allocation refusal.
  Its topology and routing also retain other structures and ownership tokens.
- [InputCapacity](../../crates/nara_input/src/timeline/capacity.rs) accounts for retained records,
  reserved terminal obligations and sequence headroom. This is semantic admission accounting,
  not simply a count of allocated bytes.

An allocator-aware scratch `Vec` could later support measured allocation attribution or enforce
a private allocation budget. Replacing only that vector would not bound the entire Input owner,
and this release does not supply a stable allocator-aware `VecDeque` migration. Preserve terminal
credits, topology validation and owner identity regardless of allocation strategy.

Only pursue a private prototype when a complete consumer exposes an allocation cost or refusal
problem worth solving. Measure peak/retained memory, allocation failures and frame-time tails
against the current implementation before promoting an allocator parameter into public module
APIs. No new allocator framework, arena, container replacement or performance claim follows from
the stabilization alone.

| `i686-pc-windows-gnu` becomes Tier 2 without host tools; `wasm32-wasip3` becomes Tier 2 ([release][release]). | Neither is Nara's inspected Windows host or the CI `wasm32-unknown-unknown` target. Do not expand support claims or replace the existing Wasm target on that basis. |

The low-level x86 Rust ABI, dyn-compatibility and unsafe-code changes in the release notes should
be considered when investigating an actual compiler/native failure. `extern "custom"` does not
establish a stable cross-version Rust plugin ABI or justify a new Nara language/runtime boundary.

## Deferred Work And Actionable Limits

Defer broad `Infallible` to `!` rewrites, boolean toggling/trim helper rewrites, blanket `Box`/`Arc`
mapping changes and unsafe ZST construction. None addresses an observed Nara product gap in this
research. Standard-library convenience is useful when touching the owning code for a concrete
reason; it is not an independent migration objective.

There is no source-proven mandatory dependency bump or MSVC installation blocker from this
bounded inspection. The actionable gap is **missing 1.100 qualification** across the existing
feature, native dependency and independent-consumer graphs. The active runtime integration and
concurrent working-tree changes make an opportunistic whole-tree build an unsuitable substitute
for that planned evidence. No native UI/DPI work is reopened by this note.

A future MSRV increase would be justified by an accepted concrete use of a newer language/std
capability, an actual required dependency, or an explicit supported-toolchain policy decision.
The currently identified Cargo benefits can first be assessed with a newer developer/CI toolchain
while preserving 1.95-compatible source and its separate verification.
