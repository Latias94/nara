## Consumer And Endpoint

The ignored private Editor test opens an explicitly supplied external copy of Collect Game and
uses ordinary public actions. Each Play begins from completed Idle/AppliedStop; source writes
are closed and the previous result is acknowledged before timing. Completion requires Running
and the next matching AppliedPlay with a fresh executable generation. Separate Restart samples
preclear the old result and require AppliedRestart with the same generation. The public view has
no request nonce; matching operation after cleared result is the observable protocol.

The endpoint is Editor observation of validated first-presentation-attested READY, not first
photons, a GPU timestamp or desktop input replay. Five-millisecond polling is included. Stop,
source writes, result acknowledgement and JSON output remain outside timing. Editor runs in its
development profile; this is not a release-Editor comparison. The game uses its production
supervised command's explicit host target, dev profile and desktop features with one build job,
incremental compilation and the shared engine target directory.

Each of no-edit, function-body and runtime-layout cohorts has one baseline Play warmup and five
retained samples. Body/layout representative source changes begin with retained sample one.
Three independent headless executions outside timing validate 62 ticks, three goals, victory,
and player x 108.0 / 108.8 / 108.8. The layout variant adds and uses an actual GameState field.
After measurements, a deliberate compiler error must produce Faulted with no active generation,
an exact compiler diagnostic and retained last-good. The desktop source is restored before the
repair Play reaches a new Running generation. Gameplay source is restored after Stop and physical
Editor close; the collector then verifies both files contain their original bytes.

## Attribution And Selected Correction

Temporary env-gated probes record six intervals within each marker-delimited action window,
using one baseline warmup and one retained sample per class. They are exploratory, with logging
and native Cargo `--timings`, and are excluded from public acceptance timings. The
[phase record](data/2026-10-20-rust-play/exploratory-phases.json) binds nextest
`826d04c0-a8fc-4edd-aef2-5448fb1570d6`. In its retained no-edit window, Cargo admission through
physical process/output cleanup takes 9.893 seconds, generation worker body 0.182 seconds and
spawn request through validated READY 1.314 seconds. Body/layout Cargo windows are 9.185/9.683
seconds. The three other identity/metadata command windows are roughly 0.08-0.15 seconds each.
These nested/partial intervals are not added or percentile-subtracted. Preparation excludes
thread admission/owner join; command intervals include those processes' physical cleanup and polling.

The [native Cargo reports](data/2026-10-20-rust-play/cargo-diagnostics.json) retain timestamped HTML
and uncompressed hashes. Static HTML identifies 263 fresh and three dirty units in the first
diagnostic cohort: gameplay plugin, game library and desktop binary. Representative plugin unit
time is 3.4 seconds, including 1.3 seconds frontend and 2.1 seconds codegen; a desktop unit takes
3.2 seconds. A binary unit's total is not a linker CPU attribution. Internal Cargo HTML JavaScript
is not treated as a machine protocol. No dependency-wide rebuild or separate job-kernel defect is
demonstrated. Preparation/publication checks remain justified, and no debug-info/profile/linker
setting is changed on this evidence.

A [second exploratory process](data/2026-10-20-rust-play/exploratory-phases-second.json)
(`d5e7eeeb-da3f-43a8-9b17-6e3c9427f1a6`) provides a counterexample
to mandatory rebuilding: its retained no-edit Cargo window is 1.822 seconds and the following
unchanged baseline is 1.315 seconds, with native reports showing 266 fresh/zero dirty units.
Thus neither all observed variability nor every repeated compile can be assigned to the Editor.
Direct CLI control and [matched verbatim-path diagnostics](data/2026-10-20-rust-play/windows-path-freshness.json)
do establish a smaller input defect: two unchanged invocations can report `PathToSourceChanged`
for the game library and desktop binary while Windows path spelling switches between canonical
verbatim and ordinary drive-letter form. The direct ordinary-path control's second invocation is
fresh. These controls are separate from public action timings.

The final [headless Cargo control](data/2026-10-20-rust-play/headless-cargo-diagnostics.json)
retains two native `--timings` reports on restored baseline source at `da76a21`, using the original
no-explicit-target headless graph. The first build has 165 fresh/three dirty units after source
restoration; the unchanged second build has all 168 units fresh. Cargo command wall times are
8.337/1.271 seconds, while native HTML displays 8.2/0.0 seconds. Both actual executables pass
62 ticks, three goals, victory and x 108.0. These are two diagnostic controls, not a new timing
cohort or a comparison against desktop Play. A warm headless graph and its three project units
are smaller than the desktop graph; their different endpoints remain explicit.

`DesktopBuildRequest` still resolves the real directory with `std::fs::canonicalize`, then uses
a new Windows-only Editor dependency on the mature `dunce 1.0.5` compatibility conversion before deriving Cargo's
CWD/manifest/lock paths. The conversion performs no I/O and retains long, non-Unicode, UNC,
device and other incompatible special paths. Filesystem capabilities, source receipts, metadata
fact matching and tool/proxy admission stay with their current owners. This stabilizes a tool
input representation; it does not weaken identity checks or promise universal cache reuse.
All private timing fields, environment gates and `--timings` branches are removed from production.

## Reproduction

Use a fresh external disposable Collect Game with engine dependency paths adjusted to this
checkout and an admitted authoring bundle. The collector refuses the maintained sample and
requires a new absolute output path. It retains logs/project data and restores its source edits.

```powershell
$env:CARGO_BUILD_JOBS='1'
$env:CARGO_INCREMENTAL='1'
$env:CARGO_TARGET_DIR='<engine checkout>/target'
$env:NARA_PLAY_COST_PROJECT='<external disposable collect-game>'
$env:NARA_PLAY_COST_OUTPUT='<fresh absolute results.json>'
cargo +1.95.0 nextest run -p nara-editor --test first_game_workflow --locked --offline --run-ignored only -E 'test(ordinary_rust_play_iteration_costs)' --no-capture
```

Nested Cargo is part of this single serial trajectory. No other Cargo command may run in the
checkout while it executes. These controlled source variants do not establish universal freshness
for Rust modules, proc macros, build scripts or environment inputs. Browser execution and a native
hot-patch ABI are not implied by this evidence.
