# Local Finite Source-Tool Releases

## Complete Consumer And Placement

Take the actual independently built EnemyStats command and health parameter facet from the
qualified Session/Inspector/panel workflow through local release preparation, installation,
explicit enablement, same-Schema V2 update, failure recovery, disable and removal. A shipped
content sample must survive modification or explicit adoption. Required installed dependents,
including disabled ones, block ordinary removal. An explicit cascade previews and revalidates
the complete affected set. Save, physical Close and fresh Open retain documents and installed
facts without treating project-controlled records as executable approval.

Select the existing finite direct-child semantic Host for this ordinary tool. The source-built
companion remains the Rust composition baseline; the current consumer names no native Editor
authority or measured throughput need that warrants a privileged native ABI. Measure one probe,
one proposal-to-review, update/failure and fallback using that same useful command. Do not build
three SDKs. The incumbent frontend supplies interaction evidence; the future Editor is drawn
by Nara and consumes the same semantic owners.

Pinned Godot `81ab961f91066a63bcbf3ec340962bb1a1ada558` separates plugin discovery from activation
in `editor/plugins/editor_plugin_settings.cpp` and `editor/editor_node.cpp`. Inspector property
and dock registrations are separate in `editor/plugins/editor_plugin.cpp`; Nara keeps its own
shared candidate and drawing model. Godot's `editor/asset_library/editor_asset_installer.cpp`
per-file extraction is no proof of owned-file update/removal or an atomic install. Pinned Bevy
`85503941e488152711a4695bbe248e9ed9f453fc` configures source-built plugins in
`crates/bevy_app/src/{plugin,plugin_group,app}.rs`; builder disable and pre-schedule cleanup are
not runtime unload. These are source comparisons, not newly executed native evidence.

## Owners And Facts

Project Session continues to own executable activation, request, candidate and physical child
retirement. Document owners retain Schema-relative preparation, inverse, history and persistence.
The concrete local release coordinator belongs to the existing product Host. It must not become
a universal Package kernel, merged source resolver, second activation owner or second Schema
validator. `nara_tooling` carries pure installed/enablement observations and actions when those
operations exist; it does not own processes, filesystem capabilities or file deletion.

The artifact receipt records a nonzero installation identifier and the selected manifest digest.
Live installation custody separately retains created members, content observations and publication
receipts. The bounded installed-content protection ledger must not infer deletion authority from
that persisted artifact receipt. Desired enablement is a durable request, not an executable trust grant.
Runtime activation IDs remain nominal Session identities. Package, Schema owner, component,
release, installed file and active invocation are distinct identities with explicit relationships.
Cargo and NuGet/MSBuild retain source resolution and build authority. Only already selected exact
local relationships are checked; unsupported sources, roles, migration and targets reject.

## Dependency-Ordered Implementation

1. **Code-free release preparation.** Capture the selected local manifest and complete declared
   artifact/content bytes through strict capabilities. Check target, finite protocol/authority,
   portable paths, aliases, required relationship declarations, aggregate payload allowance and
   every digest before returning an owned immutable candidate. Reuse Reflect catalog admission
   and the actual finite component contract. Do not execute a describe probe, write project
   metadata or construct a command from the mutable source directory. This is preparation only.
2. **Installation publication and ownership.** Preview and explicitly confirm the candidate's
   destination, content, trust, target and required relationships. Stage through the filesystem
   owner: first publish an empty no-replace candidate directory, write/verify its finite payload,
   then atomically commit an installation receipt last. Keep the candidate unready until that
   commit; this is not whole-directory-tree atomicity. Retain actual root and receipt publication
   facts, continuous created-file custody and per-file sync evidence. Installed graph selection
   and its ownership/adoption ledger remain separate from artifact publication.
   Refuse existing unowned files even when their bytes match. Modified, adopted and ambiguous
   content survive updates/removal. Handle staging or publication uncertainty without claiming
   rollback. File deletion needs exact owning proof; directory publication alone cannot grant it.
3. **Approved activation and update.** Host approval binds the selected release and external
   runtime prerequisite. Installed files and persistent enablement never approve themselves.
   The [runtime authority study](../research/2026-10-28-installed-tool-runtime-authority.md) selects
   an explicitly approved machine-managed runtime baseline, with configured root/framework/version
   and finite drift observations. It does not promise immutable transitive runtime bytes or a
   reproducible native dependency closure. Keep package-controlled inputs outside that baseline.
   First move the existing exact Windows image evidence into its root Host owner and reuse it
   from Play; do not move the Play supervisor, generation store or cleanup policy with it.
   Qualify a concrete managed bootstrap receiving captured images by a bounded stream envelope
   before the unchanged source-tool request. Do not execute package images by probing their mutable
   installation directory. Check metadata/reference identities before load and refuse unknown
   dependencies without default-context fallback. This is a finite C# adapter experiment, not a
   second source proposal owner, official SDK or universal language Host.
   `EditorSourceToolManagedHost` now prepares the explicit Windows launcher/bootstrap approval;
   `approve_installation` binds an inspection's captured images to an ordinary Session definition.
   Qualify this implementation with the actual installed V1/V2 consumer, negative metadata/graph
   probes and held acquisition/IO return. Its presence alone does not close this step or durable
   selection. Standalone approval still rejects required relationships; selected exact installed
   relationships use the installed-graph successor's Session preparation.
   Prepare exact artifact custody before invoking the existing probe; same-Schema V2 coexists
   with the predecessor until readiness and the chosen publication cut. Define receipt versus
   routing order inside the actual Session/coordinator boundary. Candidate failure preserves V1;
   post-switch retirement debt stays visible. Validate the approved launcher and runtime policy;
   an unchecked path or ordinary read-handle inventory is not installed execution custody.
4. **Disable, removal and recovery.** Revalidate installed required-dependent closure before any
   mutation. Ordinary removal blocks; an explicit confirmed cascade withdraws the affected
   routes and retains physical custody. A conservative whole-tool-lane return check is acceptable
   for this single slot if exposed honestly; unrelated resource owners are not a substitute.
   Reclaim only proven unmodified managed files after physical return; explicit adoption revokes
   deletion authority even if bytes still match. Retain cleanup/recovery facts across Close/Open.
   The [protected-content successor](2026-10-28-protected-source-tool-content-plan.md) separates
   continuous creation custody from durable protection facts and fresh explicit removal review;
   generic exact-object unlink already landed at `2f032e7`. It proves no stable-content policy;
   the separate all-stream safe reclaimer remains unresolved.
5. **Public and native consumer.** Complete the actual tool workflow without fixture-owned
   execution, installation or proposal interpretation. Exercise invalid/missing/oversized/aliased
   artifacts, wrong digest/target, failed V2, stale review, changed content, adoption, disabled
   dependents, cascade cancel/stale preview and held physical return. Run affected serial root,
   Tooling, Editor, external consumers and Windows/DX12 qualification. Record calls/latency and
   platform limits. Only then close the concrete local lifecycle unit; full R1b/Goal scope remains.

The first production API is `PreparedEditorSourceToolRelease::capture`. Its immutable bytes are
the input to installation, not authority to install or execute. It reads only declared members;
undeclared source siblings cannot become implicit installed runtime dependencies. Package authors
provide one `nara-tool.json` with explicit package/release, Host target, trusted-process authority,
protocol 1, Schema owner/component/catalog, hosted entry, exact requirements and member digests.
The first path grammar is ASCII, at most eight components and 512 bytes; case-fold duplicates and
file/directory prefix collisions reject on every platform. Ceilings are 64 KiB manifest, 64 files,
16 MiB per payload and 64 MiB aggregate, plus the existing Reflect catalog limits. This is neither
an archive reader, a resolver, a hard filesystem deadline nor an RSS sandbox.

## Schema And Content Boundaries To Preserve

Earlier EnemyStats activation fixtures pre-admitted metadata in the project's authoring bundle.
That historical evidence retains its premise. The bounded
[owner-adoption successor](2026-10-28-authoring-owner-adoption-plan.md#qualified-successor) now
qualifies missing-owner Application and native consumers through actual source/history,
bundle custody and complete Session adoption before tool enablement. Copying a catalog does not
update admitted documents or history, and no package Schema executor owns that transition.
Existing-owner evolution still needs a separate owning transaction. The first capture API
additionally accepts only a generation-one catalog, without a
predecessor input; even code-only updates over an evolved existing catalog need that input from
the actual metadata owner before qualification. Updates requiring Schema migration reject until
that owner has a qualified transaction.

Managed installation copies and explicit project import/adoption are different. An imported or
adopted sample is project-owned and survives removal; release origins or matching digests do not
restore installer deletion authority. The first release candidate's Content classification has
no project destination and by itself grants no overwrite or deletion permission.

ADRs 0047/0118 adopt immediate sticky protection at five source acceptance seams, using exact
bound project-relative source and owner content identity. Undo, baseline restoration, Save
replacement, Reopen and Discard cannot clear it. Conservative ASCII-case protection grants neither
exact-object deletion proof nor imported-origin ownership. The
[protected-content plan](2026-10-28-protected-source-tool-content-plan.md) owns qualification of
private accepted-touch retention, pre-IO fact admission, exact pending bytes/coalesced successors,
read-start-basis reconciliation, explicit `Protected` repair and independent protection/physical
pending observations without overwriting `content.operation`.

Save/Reopen/new document Close guard the owning source before effects with `Busy`/`RequiresReconcile`.
Whole physical Close advances protection before irreversible closing or Host/task shutdown.
Application retains inspection and original-basis repair on the retained Session during
Close/replacement waiting, including while a replacement opens; ordinary authoring remains gated.
Already-entered Save IO keeps its actual receipt, without a cross-file transaction. Acceptance
protects memory only; an accepted file-publication receipt supplies disk evidence. A crash before
publication may lose facts, and unsupported Windows directory sync prevents a power-failure
guarantee. This successor is being implemented; no executed successor qualification, new UI
controls, complete reclamation or completed Goal is claimed here.

## Contract And Verification Scope

Before durable selection reuses the shared file publisher, its accepted source must retain the
actual leaf handle rather than only an ID/digest pair. Read preparation transfers the same object
through admission; temporary publication acquires its retained read handle before consuming the
writer. This is the existing ADR 0070 live-object contract applied to the shared Host, not a new
storage service, lock tier or predecessor CAS guarantee. Scene, Prefab, extension documents and
metadata consumers use the same corrected handoff. Windows parent-directory rename may be refused
until the relevant file custody physically closes. Qualify these shared consumers before building
the durable selection record on that publisher.

ADRs 0047/0118 adopt release preparation and the receipt-last artifact publication boundary.
ADRs 0035/0118 now adopt the selected bounded installed-set/desired-slot replacement and exact
dependency withdrawal under its successor plan. Metadata adoption has its own qualified owner;
file reclamation requires its owning amendments when designed. ADRs 0020/0035/0114/0098 retain current source, execution and Schema
identity authority. ADRs
0050/0070 supply the filesystem rules; a new required primitive needs its own proved contract.
The July Package plan remains requirements-only beyond explicitly adopted slices. Change its
P1 wording to the selected concrete finite child rather than duplicating the tool in Rust just
to satisfy historical example language.

No compatibility aliases, old release readers, install scripts, uninstall callbacks or migration
guide. Keep historical research clearly historical and delete superseded active mechanisms when
their replacement is qualified. Record implementation/verification in immutable engineering
evidence; this plan is not proof that installation or activation has shipped.

## Artifact Publication Boundary

`EditorSourceToolInstallationPlan` retains the exact captured input and caller-issued parent/
destination for preview. Cancel performs no writes. Confirm publishes an empty, unready candidate
directory, then exclusively creates and synchronizes declared members. Every exact read capability
is opened and compared while its original created handle remains alive. The owner commits the
bounded `.nara-installation.json` through the existing no-replace temporary-file publication
primitive last; its read capability also spans that publication. This sequence replaces an
experimentally invalid whole-tree rename boundary: actual Windows rejects the populated directory
rename with writable descendants and with only retained read descendants. Do not close those
handles and pretend bare native IDs still prove creation provenance.

Before and after receipt commit, resolve the selected destination again from its original parent,
compare its continuously held root identity, and verify member names, identities and digests.
A bounded inventory rejects unknown or aliased members. Root publication, ready-receipt publication,
individual file sync and later observations remain distinct facts. Ordinary read capabilities
do not freeze writes or prove crash durability; Windows parent-directory sync remains unsupported.

`Failed` retains actual pre-ready directory-begin/publication error and any native orphan.
`Incomplete` means the empty candidate directory was published but this attempt did not commit
its ready receipt; it retains original input, root publication and acquired file custody.
`PublishedUnverified` retains both completed publications when subsequent admission fails.
No branch silently claims rollback. Unready candidates have no automatic/public deletion path:
temporary cleanup does not prove stable content or adoption status. Dropping custody closes
handles and leaves bytes for explicit reconciliation; qualified exact reclamation remains work.

Fresh receipt inspection checks a caller-selected receipt digest, decodes the bounded data and
reuses release capture plus complete inventory. It does not reconstruct created-file provenance,
admit a project Schema, satisfy dependencies or approve execution. Full local Package selection,
enable/update/removal, evolved metadata, reclaimer and UI workflow remain in progress above.

## Project-Local Selection Contract

The qualified predecessor used the existing single active tool slot and the real installed
EnemyStats V1/invalid/V2 consumer. The
[installed-graph successor](2026-10-28-installed-source-tool-graph-plan.md) now replaces its
single-member data model with a bounded installed set, exact requirement bindings and independent
optional desired slot. Its linked bounded qualification owns exact dependency-safe graph
withdrawal; the earlier single-slot evidence does not establish that successor or file reclamation.

The selected contract is a bounded project-local lifecycle record at
`.nara/source-tools/selection.json`, separate from the artifact's ready receipt. ADR 0035
reconciles settings authority explicitly: this record owns the local
installed selection and desired enabled/disabled state, with no duplicate `nara.toml` setting.
It is not a source dependency specification, an execution grant or a machine-independent package
lock. Project-external destinations remain usable by explicit session-only approval; durable
reopening outside the caller-issued project capability needs a separate concrete contract.

The successor canonical format remains 1 and is bounded to 64 KiB, 32 installed members and 128
aggregate edges, with at most 16 requirements per member. Each member binds a project-relative
installation directory, nonzero installation ID, exact ready-receipt digest, manifest digest and
package identity plus explicit requirement-to-installation bindings. The optional desired slot
names one member and enabled/disabled intent. Resolve those relationships through actual code-free
inspection with one shared capture allowance. Reject installation roots containing the fixed
selection parent; dedicated installation descendants remain valid. Do not store a native `FileIdentity`, active invocation ID, launcher path,
approval flag or deletion authority. Missing means unselected; corrupt, unsupported, oversized
and inaccessible records are distinct failures that block blind overwrite. Disabled retains the
selected installation. Fresh Open observes data and leaves enabled selections awaiting explicit
Host approval; it starts no describe probe.

Split the existing successful probe path into a private ready candidate and one route-promotion
helper. Session-only enable uses that same helper directly. Durable enable first fixes the ready
candidate, original selection observation and predecessor route, then publishes desired selection
through the existing finite Tasks and shared file Host. Record an actual published disk result
before checking whether current Session, attempt, route and Schema admission still allow promotion.
Only then replace the active route and retire its previous request/review through the existing
owner. An unready or failed candidate never writes selection. A known unpublished failure retains
V1; an uncertain publication requires explicit reconciliation. A published V2 whose promotion is
refused remains truthfully visible as disk V2 / active V1, without an automatic disk rollback.

Durable disable revokes execution and review immediately, then publishes Disabled separately.
Write failure must not restart the tool. Its result distinguishes stopped execution from a failed
durable update, and physical child/pipe retirement remains pending until the existing owner proves
return. Session Close does not rewrite the desired state. Late IO after Disable or Close may
report actual publication and cleanup facts but cannot recover route-promotion authority.
Reconciliation only admits disk data; it never grants approval or starts execution.

The Session retains two named attempt observations: Observe/Enable/Reconcile in `operation`,
and immediate/durable Disable in `disable`. Each has an original attempt and pending/terminal
outcome and survives until another operation is explicitly admitted in that same lane. A pending
Disable rejects another Disable. Publication and deferred Disable may complete together without
losing either terminal result; repeated Close cannot rewrite them. Unified cancellation completes
a durable probe by its original attempt rather than inferring ownership from its current phase.
Post-publication admission checks both the selected current parent and the retained leaf object;
matching leaf bytes/identity alone cannot rebind a publisher to a replacement parent.

The complete unit needs original-observation refusal, two installations of identical release bytes,
changed receipt/content, held publication, disk/route divergence, Disable/Close during publication,
write failure while stopped, and fresh Open without execution. Extend the independent Session,
Application and selected native Inspector/panel consumer. Preserve one executor, proposal owner,
history and physical close path; evolve the owning ADRs and implementation ledger with actual
results. The [selection qualification](../knowledge/engineering/verification/2026-10/2026-10-28T012206Z-durable-installed-source-tool-selection-and-independent-paired-attempt-qualification-3a4a90d3cc3042e5b89e8fa20e314c22.md)
owns the implemented single-slot scope and its actual evidence. It does not close installed
dependency selection, metadata adoption/evolved lineage, protected-content removal or this full
lifecycle plan.
The installed-graph successor separately qualifies exact required selection and reviewed graph
withdrawal. Metadata adoption has its separate generation-one owner evidence. Protected-content
reclamation, evolved lineage and the full local lifecycle remain open.
