# Installed Source-Tool Relationships And Withdrawal

## Consumer And Decision

Extend the actual EnemyStats installation consumer with A1 and A2 containing the same release
and distinct installation receipts, and B explicitly requiring A1. Register all three without
execution, approve and run B through the existing managed Host, disable B, and refuse ordinary
withdrawal of A1 because disabled B still depends on it. A dropped cascade review changes nothing;
another graph mutation makes an old review stale. A newly confirmed cascade withdraws A1 and B,
retains A2 and source/history, waits honestly for actual child return, and survives fresh Open
without restoring executable approval. Withdrawal changes installation selection, not files.

Evolve `.nara/source-tools/selection.json` rather than add an installed-set file beside it. One
bounded snapshot owns installed members, explicit requirement bindings and the optional desired
execution slot. A separate file would introduce publication ordering and reconciliation between
two authorities without a useful independent consumer. The canonical format remains version 1;
remove the previous unreleased single-member reader. The existing single active process slot,
probe, source proposals, history, file publisher and physical close owner remain.

Each graph member retains its project-relative directory, nonzero installation ID, exact receipt
and manifest digests, package and explicit package-to-installation requirement bindings. Actual
inspection must match every manifest declaration and exact bound target. Same release bytes do
not choose an installation. Disabled and nonselected members stay in the graph. Reject duplicate
IDs/directories, overlapping installation directories, missing targets, mismatched packages or
manifests, duplicate/extra bindings and cycles. Keep installation relationships separate from
Cargo/NuGet resolution, executable approval, Schema ownership and file reclamation.

## Responsibility And Interfaces

Pure request/view types live in Tooling. The concrete private graph/format belongs to the existing
Session selection owner. Code-free preparation accepts a nominal selection basis, Host-issued
project capability and finite additional installation requests. It captures actual declarations
under one shared allowance and produces an owned additive successor. Confirmation rechecks the
original basis and project object, then republishes through the existing Tasks/file owner. An
existing member can be repeated only with identical facts/bindings; registration cannot withdraw
or silently rebind it. Ordinary installed enable can register a requirement-free member as part
of the same publication, preserving its existing useful workflow.

Required tools must first belong to the current complete admitted graph. Session preparation
checks their actual required closure and asks the managed Host to approve the selected captured
images. The public standalone approval continues to refuse unresolved requirements. A prepared
required enable retains its original graph observation and rejects after graph drift. Readiness,
publication and route promotion preserve existing exact fences; all selected required facts are
revalidated before publication. Requirements mean required installation, never automatic tool
execution or a shared managed assembly search path. Each release still captures all its own
assembly references, with no unknown/default-context loading fallback.

Withdrawal preparation is a read-only, move-only review over the original nominal graph and
complete reverse required closure, including disabled members. RejectDependents refuses a
nontrivial closure; Cascade exposes the exact affected entries. Confirmation rechecks the basis
and current route before any mutation. It fences competing tool work, withdraws affected routing
and review, then publishes the complete successor. A failed durable update does not restart a
withdrawn route. Publication uncertainty retains evidence and stops affected execution until
explicit reconciliation. Normal source editing remains usable. A conservative whole-tool-lane
physical-return observation is acceptable and must be reported separately from graph publication.

Current installed artifacts need not be intact to withdraw a broken graph member: withdrawal
cannot authorize file deletion. The original selection leaf and exact graph are the publication
basis. Reconciliation observes current graph data and revokes an installed route whose exact
required facts no longer exist. It grants no approval and starts no code.

## Bounds And Acceptance

The selection snapshot is at most 64 KiB, with 32 members, at most 16 outgoing requirements per
member and 128 aggregate edges. The existing per-release limits remain. Code-free graph capture
uses a shared 128 MiB byte-work allowance, charged before receipt/manifest/payload allocation and
retained across failed reads; it does not multiply the per-release allowance by the member count.
This bounds modeled captured bytes, not RSS, filesystem latency or native allocation isolation.
Read-only graph operations use the bounded graph, not a dependency solver or generic graph service.

Qualify graph/format counterexamples, exact repeat/add behavior, two same-release installations,
disabled reverse dependents, stale/cancelled cascade review, failed publication, external record
drift, Close during publication and actual physical return. Exercise Session and Application plus
the independently compiled real managed consumer. Run serial focused nextest, relevant feature
checks and selected native qualification when the actual frontend path changes. Record actual
results and their source/platform limits in immutable evidence and the implementation ledger.

## Subsequent File Reclamation

The local lifecycle still needs created/managed/protected content facts and fresh explicit removal
review, plus a proved filesystem operation that validates and removes the same held object.
Modified/adopted samples, unknown files and dirty document-owned sources must survive. No receipt,
graph withdrawal, historical native ID or equal digest grants deletion authority. Keep that next
consumer separate from graph publication; do not add a name-based or recursive deletion fallback.
