# Concrete EnemyStats Semantic Tool Consumer

## Workflow And Authority

Extend the existing independently built C# experiment with a concrete EnemyStats tool. The
authored module describes its complete Schema and creation template using the existing catalog
format. Rust admits that metadata and uses the public Scene data family. This is experimental
consumer evidence for R1/R1b/R3, not selection of an official SDK or completion of those tracks.
The [qualification record](../knowledge/engineering/verification/2026-10/2026-10-27T152916Z-concrete-enemystats-semantic-proposals-through-the-public-project-session-1acb9412a2544e98b059654fe5ec2ca7.md)
owns actual results, independent-review corrections and the remaining product boundaries.

The window-free Project Session captures the exact document-query basis and reads stable
properties. C# receives copied scalar observations and returns a small named proposal containing
EnemyStats property writes. Rust retains the requested target and command, original query basis
and exact executable-publication and newest-request identities. Neither document authority nor source IDs are supplied
by the returned proposal. Commands cover Attach, edit and additive Spawn through existing
construction/prepared-edit owners. Review exposes the prepared patch and inverse; acceptance
consumes that same candidate and returns its actual publication result and local-entity mapping.

Do not refresh a stale query before prepare or commit. Executable replacement/disable invalidates
pending proposals and prepared tool results independently of document revision. Do not create a
new transaction executor, Undo store, language backend, generic wire SDK or toolkit panel API.
Nara's future custom-drawn frontend can consume the same UI-neutral domain operations.

## Delivery And Verification

1. Extend the existing collectible .NET bridge with the concrete tool's metadata and proposal
   calls. Reuse its serial call/lifetime owner; keep behavior callback admission independent.
2. Reuse the existing temporary-project fixture for real JSON/RON Open, history, Save and
   physically closed fresh-Host Reopen. Add the finite Host proposal consumer, with bounded
   output, stable-property writes, owner-created construction and exact result handling.
3. Prove preview without mutation, one Undo/Redo transaction, late invalid-write rejection,
   stale query and prepared-result refusal, execution-publication replacement/disable refusal,
   complete sibling persistence and actual public Rust materialization/read of the saved data.
4. Independently review the consumer and affected contracts. Run the serial language runner and
   affected focused tests/Clippy, inspect diffs, record evidence and commit locally.

The output is a trusted in-process experiment: a finite response buffer and finite declaration
counts bound accepted proposals, not authored computation or arbitrary managed allocation. Actual
install/update/remove, dependency cohorts, pending asynchronous tasks, custom Inspector drawing,
compiled Editor UI integration and clean-machine runtime deployment remain subsequent workflows.
No compatibility reader, alias or migration guide is required for superseded fixture code.

## Owning Follow-up

The concrete consumer exposed a preparation ergonomics gap: Session methods took document and
revision, while observation-driven callers separately validated the complete query basis. The
[observation-bound preparation successor](2026-10-27-observation-bound-preparation-plan.md)
owns its replacement through Workspace/Session/Application and Panel, with no compatibility
aliases. The Scene owner's revision/candidate API remains responsibility-local.
Keep executable/request identity in the actual tool owner rather than adding language generations
to every Scene transaction. Product admission and a standalone tool loader remain separate work.
